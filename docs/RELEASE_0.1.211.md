# 0.1.211 — 空心 plot 记录误报未加载

用户巨构通过扫描预算后出现「请先加载所有相连部件」。审查确认为预检查逐个要求包围盒矩形中所有chunk满足level.hasChunk，而Sable plot可以合法存在未分配的空气chunk；这类chunk.hasChunk返回false，但getChunkFutureMainThread返回原生EmptyLevelChunk。Photomancy LevelAccelerator读取包围盒本来支持空区块。

改为检查每个真实身体的getLoadedChunks列表非空，列表内实际分配区块必须能够由服务器读取；包围盒里的未分配空洞不再拒绝。原生exportSelected及placement不改变，不强制加载、不填充空气chunk，也不跳过真正的结构数据验证。世界重生区域的未加载暂停规则不改变。管理员、数量/数据预算、间隔最低5秒及滚轮±1秒不改变。

回归在真实244方块框架plot上扩展缓存包围盒，明确制造含未分配chunk的空气区域。断言hole的holder为空、hasChunk=false；随后原生Photomancy捕获及记录保存加载成功、方块数仍244、2MiB方块实体数据仍完整，导出前后allocated chunk数量不变且hole仍不存在。此前测试框架没有明确断言存在未分配chunk，因而未覆盖这个误判。

开发0.1.211，手册63；稳定0.1.200。用户世界未修改，仍需重新记录截图巨构并验证实际数据限制及重生。

## 挂载炮体和雷达清除

Photomancy用于记录/原生增量重建；死亡清理由本模组归属队列及Sable原生结构删除负责。旧整plot删除只按两个CBC基类完整名字识别炮台，继承类可能漏掉；Create Radar实际RadarBearingBlockEntity继承MechanicalBearingBlockEntity，也未覆盖其movedContraption。Radar的SmartMountBlockEntity继承CBC炮台，但在此版JAR未找到注册引用，因此只能说存在继承边界缺口，不能直接认定截图实际炮台必然属于这个类。

新增死亡专用MountedContraptionCleanup：CLEANING上下文、控制方块已登记owner，且对应owner或part在LifeLifecycle有死亡记录才准许；整plot路径还核对控制器实际属于待删除的准确body。仅清理控制器直接引用的炮体/运动结构，不查找周围实体、不接管独立结构。CBC类型识别沿继承链；机械轴承清空movedContraption、running及待装配标志，先discard附属实体，避免后续拆卸把它还原为世界方块。逐块fallback同样执行受限预清理，普通disassemble保持。

最初未逐个验证owner的方案被自动审批拒绝，理由是可能误删独立结构挂载物；上述收紧方案获准执行。验证包括真实CBC5.11.7、CBC先进技术0.1.4c重型/双管contraption类型、Radar0.4.9.4真实注册轴承、用真实SmartMount子类构造的继承边界夹具（不冒充其注册路径）、整plot及逐块清除、无归属/未死亡保护、普通拆卸。炮体payload是相应真实类型加最小测试方块，不冒充完整用户炮膛结构。整合包中的其他附属类型仍需回测。

首次挂载测试因缺少本地CBC前置而未执行，修复依赖后仍核对required-tests结果，不把Gradle退出成功当作测试通过。初始化期间发现普通接口放在Mixin包导致类加载拒绝，接口移至compat边界后再测。两种炮体同一tick立即删除/复用plot的组合夹具出现干扰，改为独立批次并断言原生attach成功，没有跳过清除断言。

最终验证：58单元、39组合（31重生相关＋8真实挂载）、使用Toolgun/Copycats删除分支39组合、真正无Photomancy40项及完整默认290项GameTest通过；手册63及构建通过。用户截图实物仍需回测，原世界未修改。
